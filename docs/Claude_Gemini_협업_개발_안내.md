# Claude Code + 안티그래비티 CLI(Gemini) 협업 개발 안내

> 이 문서는 Claude Code에게 그대로 주는 작업 안내서다.
> Claude는 **감독·검토자**, 안티그래비티 CLI(`agy`)로 실행하는 Gemini는 **구현 작업자**, 사용자는 **결정권자**다.
> 처음 한 번은 「0. 연결」부터 끝까지 순서대로 진행하고, 그 뒤로는 「3. 작업 한 건의 흐름」을 반복한다.

---

## 0. 안티그래비티 CLI 연결 (처음 한 번)

### 0-1. 설치 확인
1. 사용자 컴퓨터에 안티그래비티(Antigravity)와 CLI가 설치되어 있어야 한다. Windows 기준 실행 파일 위치 예: `C:\Users\<사용자>\AppData\Local\agy\bin\agy.exe`
2. 터미널에서 확인한다.
   ```bash
   agy --version
   ```
   ```bash
   agy --help
   ```
3. `agy`를 찾지 못하면 PATH가 잡히지 않은 것이다. 설치 폴더의 `agy install`을 한 번 실행하면 PATH와 셸 설정을 잡아 준다. 그 뒤 터미널을 새로 연다.
   - Claude Code의 Bash(Git Bash)에서도 `which agy`로 잡히는지 확인한다. 안 잡히면 전체 경로로 부른다.

### 0-2. 로그인
- 처음에는 사용자가 터미널에서 `agy`를 그냥 실행(대화형)해서 계정 로그인을 끝낸다. **로그인은 사용자가 직접 한다.** Claude는 비밀번호나 토큰을 입력하지 않는다.

### 0-3. 모델 확인
```bash
agy models
```
- 예시 출력: `gemini-3.8-flash-high`, `gemini-3.8-flash-medium`, `gemini-3.8-flash-low` 등. 사용자가 쓸 모델을 정한다(기본 추천: `gemini-3.8-flash-medium`. 어려운 설계는 `-high`).
- 기본 모델은 `~/.gemini/antigravity-cli/settings.json`의 `"model"`에 있다. 명령마다 `--model`로 지정하는 편이 안전하다.

### 0-4. 연결 시험 (비대화 모드)
```bash
agy -p "OK 한 단어만 답하라." --model gemini-3.8-flash-low --output-format json --print-timeout 150s --disable-slash-commands
```
- 정상이면 이런 JSON이 나온다.
  ```json
  {"conversation_id":"…","status":"SUCCESS","response":"OK\n","duration_seconds":4.4,"num_turns":1,"usage":{…}}
  ```
- 읽을 칸: `conversation_id`(대화 잇기용), `status`, `response`(답), `usage`(토큰).

### 0-5. 알아 둘 옵션 (agy 1.4 기준, `agy --help`로 다시 확인)
| 옵션 | 쓰임 |
|---|---|
| `-p "<지시>"` | 비대화 모드로 한 번 실행하고 끝낸다 |
| `--model <모델>` | 모델 지정 |
| `--output-format json` | 결과를 JSON 한 덩어리로 받는다 |
| `--conversation <ID>` | 앞 대화를 이어서 실행(계획 → 구현을 같은 대화로) |
| `--mode accept-edits` | 파일 수정을 자동 승인. 구현 단계에서만 쓴다 |
| `--print-timeout <시간>` | 제한 시간(0이면 끝날 때까지). 긴 작업은 0 |
| `--disable-slash-commands` | 지시문 속 `/` 문구가 명령으로 바뀌는 것을 막는다 |
| `--add-dir <폴더>` | 작업 폴더 밖의 폴더를 읽게 할 때 |
| `--effort <low~max>` | 추론 강도 |
| `--sandbox` | 터미널 명령을 제한한 샌드박스에서 실행 |
| `--dangerously-skip-permissions` | 모든 도구 사용을 자동 승인. **사용자가 명시적으로 허락했을 때만** |

### 0-6. 권한 문제 (가장 먼저 부딪히는 문제)
- 비대화 모드(`-p`)에서는 Gemini가 명령어 실행(터미널) 허락을 사용자에게 물을 수 없다. 그래서 **명령 실행이 자동 거부되고 빈 답이나 반쪽 결과가 온다.**
- 대응(위에서부터 우선):
  1. 지시문에 **읽을 파일의 정확한 경로**를 적고 "파일 찾기·명령어 실행 도구는 쓰지 말 것"을 명시한다. 빌드·테스트는 Gemini가 아니라 **Claude가 직접** 돌린다.
  2. 꼭 명령이 필요하면 `--sandbox`로 제한해 실행하거나, agy 설정의 허용 규칙을 사용자와 함께 정한다(형식은 agy 문서 확인).
  3. `--dangerously-skip-permissions`는 사용자 허락 없이 쓰지 않는다.
- `--mode plan`은 쓰지 않는다(계획 슬래시 명령으로 바뀌어 원하는 결과가 안 나온 적이 있다). 계획만 원하면 지시문에 "계획만 내고 멈춰라"라고 쓴다.

### 0-7. 작업 폴더 준비
프로젝트 안(또는 옆)에 아래를 만든다. 이름은 바꿔도 된다.
```
<프로젝트>/
  docs/기준문서.md          ← 아키텍처·규칙·현재 상태 (Gemini가 매번 먼저 읽음)
  docs/작업목록.md          ← 쪼갠 작업 목록과 진행 상태
  .agy-work/                ← 지시문·응답 보관 (git에 넣지 않으려면 .gitignore에 추가)
    012_1_계획요청.txt
    012_1_계획응답.json
    012_1_계획.md
    012_2_구현요청.txt
    012_2_구현응답.json
    012_3_수정요청.txt …
  scripts/verify.(sh|ps1)   ← 기계 검증 한 방에 돌리는 스크립트
```

### 0-8. 기계 검증 스크립트 준비 (필수)
- 프로젝트에 맞는 명령을 `scripts/verify`에 모은다. **이 스크립트가 0으로 끝나야 "완료"다.**
  ```bash
  # 예시 (프로젝트에 맞게 바꾼다)
  set -e
  npm ci            # 또는 pip install -r requirements.txt 등
  npm run build
  npm run lint
  npm run typecheck
  npm test
  npx prettier --check .
  ```
- 보호 경로(건드리면 안 되는 폴더·파일) 목록을 두고, 매 작업 후 `git diff --name-only`에 그 경로가 없는지 검사하는 줄도 넣는다.

### 0-9. 자동 훅 (권장)
- **git pre-commit 훅**: 커밋 전에 `scripts/verify`를 돌리고 실패하면 커밋을 막는다.
- **Claude Code Stop 훅**: Claude가 작업을 끝낼 때 검증을 돌린다. `.claude/settings.json` 예시(형식은 Claude Code 문서로 확인):
  ```json
  {
    "hooks": {
      "Stop": [
        { "hooks": [ { "type": "command", "command": "bash scripts/verify.sh" } ] }
      ]
    }
  }
  ```
  훅이 실패 코드로 끝나면 Claude가 그 출력을 보고 계속 고친다.
- **CI**: 같은 스크립트를 CI에서도 돌린다.

## 1. 역할

| 누가 | 하는 일 | 하지 않는 일 |
|---|---|---|
| **사용자** | 무엇을 만들지 정한다. 계획·결과를 보고 지적한다. 로그인·결제·배포 승인 | – |
| **Claude(감독)** | 작업 쪼개기, 지시문 작성, agy 실행, 계획 검토, **기계 검증 직접 실행**, diff 검토와 수정, 기준 문서 갱신, 보고 | Gemini의 "통과했다"는 말을 그대로 믿기, 사용자 대신 큰 결정 |
| **Gemini(작업자)** | 계획 작성, 구현, 지적받은 곳 수정 | 범위 밖 파일 수정, 기준 문서 수정(지시 없으면), 명령 실행(권한 없음) |

작업자와 검토자를 나누는 이유: 쓴 쪽과 보는 쪽이 다르면 실수가 잘 걸린다.

---

## 2. 작업 쪼개기

- 큰 요구는 먼저 `docs/작업목록.md`에 **작은 작업**으로 쪼갠다. 한 작업 = 한 PR 크기(한 기능, 관련 파일 몇 개).
- 작업마다 적는다: 번호와 이름표, 목표, 시작 상태, **완료 조건(통과해야 할 테스트·검사)**, 고쳐도 되는 파일 범위, 하지 말 것.
- 이름표는 번호 대신 `[인증-1]`, `[인증-2]`처럼 붙인다. 중간에 작업을 끼워 넣어도 이름표는 그대로다. 더 쪼개면 `[인증-1-1]`.
- 한 번에 너무 많이 맡기면 Gemini가 대충 훑고 지나간다. 결과가 얕으면 작업을 더 쪼갠다.
- 다음 작업의 일을 당겨 하지 않게 "여기서 끝낸다"를 적는다.

## 3. 작업 한 건의 흐름

### 3-1. 지시문 작성 (`NNN_1_계획요청.txt`)
템플릿은 「5. 템플릿」. 반드시 넣을 것:
- 읽을 파일의 **정확한 경로** 목록(기준 문서, 관련 소스, 관련 테스트)
- 목표와 완료 조건
- 고쳐도 되는 파일 범위 / 건드리면 안 되는 경로
- "코드를 쓰지 말고 계획만 내고 멈춰라"
- "명령어 실행 도구는 쓰지 않는다"

### 3-2. 계획 요청
```bash
cd <프로젝트> && agy -p "$(cat .agy-work/012_1_계획요청.txt)" --model gemini-3.8-flash-medium --output-format json --disable-slash-commands > .agy-work/012_1_계획응답.json
```
- 10~30분 걸릴 수 있다. **백그라운드로 실행**하고 끝나면 이어서 처리한다(Claude Code의 백그라운드 실행 사용).
- 끝나면 `response` 칸을 `012_1_계획.md`로 저장하고 `conversation_id`를 적어 둔다.
  ```bash
  python -c "import json;d=json.load(open('.agy-work/012_1_계획응답.json',encoding='utf-8'));print(d['status'],d['conversation_id']);open('.agy-work/012_1_계획.md','w',encoding='utf-8').write(d['response'])"
  ```

### 3-3. 계획 검토 (Claude)
확인 목록:
- [ ] 존재하지 않는 함수·파일·설정·API를 지어내지 않았는가 → 실제 파일과 대조
- [ ] 고쳐도 되는 범위를 넘지 않는가
- [ ] 기준 문서의 규칙(아키텍처, 이름 규칙, 금지 패턴)을 지키는가
- [ ] 완료 조건을 실제로 만족시키는 계획인가
- [ ] 테스트를 지우거나 건너뛰는 계획이 없는가
- [ ] 다음 작업의 일을 당겨 하지 않는가
- 사용자가 관여하길 원하면 이 시점에 계획 요약을 보여 주고 확인받는다.

### 3-4. 구현 요청 (같은 대화로)
```bash
cd <프로젝트> && agy -p "$(cat .agy-work/012_2_구현요청.txt)" --model gemini-3.8-flash-medium --output-format json --disable-slash-commands --conversation <계획의 conversation_id> --mode accept-edits > .agy-work/012_2_구현응답.json
```
- 구현요청에는 **"계획에서 고칠 것" 번호 목록**을 넣는다(체크리스트로 쓰기 위해).
- `status`가 ERROR로 끝나도 파일은 완성되어 있는 경우가 있다. **상태 값이 아니라 실제 파일·diff로 판단한다.**

### 3-5. 기계 검증 (Claude가 직접, 가장 중요)
```bash
bash scripts/verify.sh
```
```bash
git diff --stat
```
- **완료의 정의: 빌드·린트·타입·포맷·테스트가 모두 통과.** 하나라도 실패하면 완료라고 보고하지 않는다.
- Gemini가 "테스트 통과했다", "다 고쳤다"고 해도 믿지 않는다. 직접 다시 돌린 출력으로 판단한다.
- 실패하면 오류 출력 전체를 붙여 같은 대화로 수정 요청(`NNN_3_수정요청.txt`)을 보내고, 다시 직접 돌린다.
- **같은 실패가 두 번 반복되면** Claude가 원인을 직접 찾아 고친다(작업자에게 계속 돌려보내지 않는다).
- 아래 diff는 따로 짚고 사용자에게 알린다:
  - 테스트 삭제, 테스트 건너뛰기(skip/only), 기대값을 결과에 맞춰 바꾼 것
  - 린트·타입 규칙을 끄는 주석(`eslint-disable`, `# type: ignore`, `@ts-ignore` 등)
  - 보호 경로의 변경, 범위 밖 파일 변경
  - 의존성 추가·버전 변경, 설정 파일 변경

### 3-6. diff 검토 (Claude, 기계가 못 보는 것)
- 설계가 기준 문서와 맞는가, 이름·구조가 주변 코드와 같은 결인가
- 요구를 정말 만족하는가(테스트가 요구를 제대로 표현하는가)
- 3-4의 "고칠 것" 목록이 **하나도 빠짐없이** 반영됐는가 → 하나씩 확인
- 불필요한 변경, 죽은 코드, 과한 추상화
- 작은 것은 Claude가 직접 고치고, 고친 뒤 3-5를 다시 돌린다.

### 3-7. 기록과 보고
- `docs/작업목록.md`에 상태 갱신(완료/남은 것/보류).
- 새로 정해진 규칙은 `docs/기준문서.md`에 넣는다(→ 「4. 규칙 승격」).
- 커밋(사용자가 원하면). 커밋 메시지에 작업 이름표.
- 사용자 보고 형식(짧게):
  1. 무엇을 했는지
  2. 실행한 검증 명령과 결과(통과/실패 수)
  3. Gemini 결과에서 Claude가 고친 것
  4. 확인하지 못한 것, 사용자가 결정할 것

---

## 4. 규칙 승격 (같은 실수를 두 번 안 하게)

- 사용자가 한 번 지적한 것은 말로만 기억하지 않는다. 다음 셋 중 맞는 곳에 넣는다.
  1. **테스트**: 지적된 버그는 고치기 전에 그 버그를 재현하는 테스트를 먼저 추가한다(회귀 테스트).
  2. **린트·검사 스크립트**: 금지 패턴(금지 함수, 금지 import, 금지 경로)은 자동 검사에 넣는다.
  3. **기준 문서**: 설계 원칙·이름 규칙처럼 기계로 못 잡는 것.
- 지시문의 공통 꼬리말(「5-4」)에도 반영한다. 기준 문서와 꼬리말을 같이 고친다.

## 5. 템플릿

### 5-1. 계획 요청
```
작업 폴더는 <프로젝트 경로>다.
아래 파일을 파일 보기 도구로 끝까지 읽는다. 경로가 정확하니 파일을 찾는 명령어는 쓰지 않는다. 명령어 실행 도구는 이 작업에서 쓰지 않는다.
- <프로젝트>/docs/기준문서.md
- <관련 소스 경로 1>
- <관련 소스 경로 2>
- <관련 테스트 경로>

이 작업은 작업목록의 [<이름표>]다.
목표: <한두 문장>
완료 조건: <통과해야 할 테스트·검사, 동작>
고쳐도 되는 파일: <목록>
건드리면 안 되는 경로: <목록>
하지 말 것: <예: 공개 API 시그니처 변경, 의존성 추가>

지금은 코드를 쓰지 말고 변경 계획만 내고 멈춘다. 파일은 만들거나 고치지 않는다.
계획 형식:
1. 첫 줄에 읽은 파일 목록
2. 파일별 변경점(무엇을, 왜)
3. 추가·수정할 테스트
4. 위험과 확인이 필요한 점
5. 사실 확인 칸: 계획이 기대는 기존 함수·설정마다 근거 파일과 위치

<공통 꼬리말>
```

### 5-2. 구현 요청
```
계획을 확정하고 구현한다.
```

### 5-4. 공통 꼬리말 (모든 지시문 끝에 붙인다)
```
지킬 것.
- 지시문의 예시 코드는 형태만 보여 준 것이다. 그대로 붙여 넣지 말고 이 프로젝트 코드에 맞게 짓는다(그대로 쓰라고 표시한 것만 예외).
- 존재하지 않는 함수·파일·설정을 지어내지 않는다. 확실하지 않으면 계획의 확인 칸에 적는다.
- 고쳐도 되는 파일 밖은 건드리지 않는다. 포맷만 바꾸는 변경도 하지 않는다.
- 테스트를 지우거나, 건너뛰게 하거나, 기대값을 결과에 맞춰 바꾸지 않는다. 린트·타입 규칙을 끄는 주석을 넣지 않는다.
- 의존성 추가, 설정 파일 변경은 계획에 먼저 적고 승인받는다.
- 다음 작업의 일을 당겨 하지 않는다.
- 기준 문서(docs/기준문서.md)의 규칙을 따른다.
```

## 6. Gemini의 버릇과 대응 (실제로 겪은 것)

| 버릇 | 대응 |
|---|---|
| 지시문의 예시를 그대로 베낀다 | 예시는 "형태만" 설명. 그대로 쓸 것만 "그대로"라고 표시 |
| 계획의 메모 줄을 결과물에 그대로 옮긴다 | "계획의 메모를 코드·주석에 옮기지 말 것" 명시 |
| 고치라고 한 것 중 일부를 빠뜨린다 | 번호 목록으로 주고, 결과에서 하나씩 확인 |
| 없는 함수·설정·사실을 지어낸다 | 계획에 근거 위치를 적게 하고 대조 |
| 범위 밖 파일까지 고친다 | 허용 파일 목록 명시 + `git diff --name-only`로 확인 |
| "다 통과했다"고 말한다 | 믿지 않고 직접 실행 |
| 한 번에 많이 맡기면 얕게 훑는다 | 작업을 더 작게 쪼갠다 |
| 상태가 ERROR여도 파일은 완성된 경우 | 상태 값 대신 파일·diff 확인 |
| 서버가 느려 한 호출에 몇 분씩 걸린다 | 백그라운드 실행, 서두르지 않기. 시간이 너무 길면 작업을 쪼갠다 |

## 7. 실행 중 방향이 바뀔 때

- 사용자가 실행 중에 방향을 바꾸면: 실행 중인 agy 작업을 **멈춘다** → 지시문을 고친다 → 다시 보낸다.
- 멈추기 전에 이미 파일이 바뀌었을 수 있으니 `git status`·`git diff`로 확인하고, 필요하면 되돌린 뒤 다시 시킨다(되돌리기 전 사용자 확인).
- 이미 잘 나온 부분이 있으면 "이 부분은 그대로 두고 저 부분만 다시"라고 범위를 좁혀 다시 시킨다.

---

## 8. 안전 규칙

- 로그인, 비밀번호, API 키, 결제는 사용자가 직접 한다. 지시문에 비밀 값을 넣지 않는다(환경 변수 이름만 적는다).
- 보호 경로는 매 작업 후 diff로 확인한다.
- 되돌리기 어려운 일(강제 푸시, 데이터 삭제, 배포)은 사용자 확인 후에만.
- 작업 전 상태는 git 브랜치나 커밋으로 남긴다.
